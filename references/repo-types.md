# 저장소 유형별 정제 절차

유형을 판정한 뒤에 해당 절이면 충분하다. 전부 읽을 필요는 없다.

판정 요약: 민감한 것이 **사고로 섞인 흔적**이면 A, **정본의 정당한 내용**이면 B, **코드가 먹는 입력 데이터**면 C.

---

## A. 동일 파일 공개형 (in-place)

정본과 공개본이 같은 파일이다. 개인용으로 시작한 스킬·라이브러리·CLI가 공개로 포지셔닝이 바뀐 경우가 대부분이다.

**전제**: 민감 정보는 애초에 없어야 했다. 있다면 사고이므로 그 자리에서 제거한다. 사본을 따로 두지 않는다.

### 절차

1. 스캐너 전 축을 돌린다. 축 3(로컬 경로)·축 4(결합)이 여기서 가장 많이 걸린다.
2. 발견을 세 갈래로 나눈다.
   - **제거**: 개인 경로·계정·크리덴셜. 남길 이유가 없다.
   - **일반화**: 저자 개인 설정에 결합된 안내. "글로벌 설정의 X 항목에서 가져온다"를 호출 인자(`--image <path>`)로 바꾼다. 외부 사용자에게는 그 설정이 존재하지 않으므로 원문 그대로면 문서가 거짓말이 된다.
   - **허용**: 공개 핸들, 공개 저장소 이름, README의 설치 예시 경로, 업스트림 공개 저장소 링크. `.sanitize.local.md`의 `## 허용`에 근거와 함께 등록한다.
3. 머신 종속 하드코딩을 폴백 사슬로 바꾼다: **환경변수 > 글롭 > PATH**. 버전이 박힌 절대경로(`jdk-21.0.10.7-hotspot`)는 저자 컴퓨터에서만 참이다.
4. 개인 데이터가 든 샘플 파일은 커밋하지 않는다. 예제가 필요하면 합성 데이터를 만든다.
5. `.gitignore` 분리를 유지한다: 개인 교훈 로그, 저작권 자료, 서드파티 바이너리, 작업 부산물.

### 지속 규율

공개 전환은 여기서 끝나지 않는다. 정본이 곧 공개본이므로 **편집할 때마다** 새 흔적이 들어온다. 개인 환경에서 쓰다가 그 경험을 그대로 문서에 적는 것이 가장 흔한 유입 경로다. pre-commit 훅으로 스캐너를 걸어 두는 것을 권한다(`tools.md` 참조).

### 결합 판정의 경계

같은 컴퓨터의 **개인** 도구를 가리키는 것은 금지지만, 한 공개 패키지가 다른 **공개** 패키지에 정식 의존하는 것은 정상이다. 기준은 "외부 사용자가 이것을 설치할 수 있는가"다. PyPI·npm 패키지명이나 공개 저장소 참조는 남기고, 개인 스킬 디렉터리 내부 파일 참조는 일반 서술로 바꾼다.

## B. 정본/반출본 분리형 (export)

민감 정보가 정본의 정당한 내용이다. 저자는 실명·기관명·문서번호가 든 정본을 계속 실사용해야 하고, 공개본은 그것의 치환 사본이다. 업무 자동화 스킬처럼 "절차 지식은 공개 가치가 크지만 그 절차가 특정 조직에 붙어 있는" 경우가 전형이다.

**전제**: 정본은 비공개 위치에 남고, 공개 저장소에는 절대 들어가지 않는다. 두 트리가 물리적으로 다른 것이 이 유형의 핵심 안전장치다. 반출본은 정본 히스토리를 물려받지 않으므로 3단계(히스토리 판정)의 위험을 구조적으로 회피한다.

### 절차

1. **정본에서 변경분만 복사한다.** 드라이브 잡파일(`desktop.ini`·`.DS_Store`)은 제외.
2. **치환한다.** 삭제가 아니라 역할·일반형으로 바꾸는 것이 원칙이다.

   | 정본 | 반출본 |
   |---|---|
   | 실명 | `○○담당관`·`담당 교사` 등 역할 |
   | 기관명 | `○○중학교`·`○○과` |
   | 결재라인 실명 표 | `기안 → 부장 검토 → 교감 검토 → 교장 결재` |
   | 문서번호·계정 ID·연락처 | 형식만 남기고 값 제거 |
   | 개인 로컬 경로 | 인자·환경변수로 |

   **워크플로 교훈은 보존한다.** 소요 시간, 화면 전환 순서, 시행착오, 함정은 개인정보가 아니라 이 공개본의 존재 이유다.

3. **조합 식별을 본다.** 개별 항목이 다 익명이어도 사업명·예산 규모·학년 구성·지역이 겹치면 기관이 특정된다. 이건 스캐너가 못 잡는 판단 영역이라 사람이 읽어야 한다.
4. **스윕한다.** `scan_traces.py --axes custom`으로 잔여 리터럴을 확인한다. 대량 치환이면 `--apply --yes`를 **반출본에서만** 돌린다.
5. **커밋한다.** 의도 파일만 pathspec으로(`git commit -- <경로>`).

### 반복 반출

정본이 갱신될 때마다 1~5를 다시 돈다. 정본 갱신을 반출본에 직접 반영하고 싶은 유혹이 크지만, 그러면 두 트리의 방향이 뒤집혀 다음 반출에서 치환 전 내용이 되돌아온다. 흐름은 항상 정본 → 반출본 한 방향이다.

### 공개본 자체의 갱신 규율

공개본 파일을 편집할 때는 처음부터 일반화된 형태로 쓴다. 정본 표현을 적어 놓고 나중에 치환하는 순서는 반드시 새는 경로가 생긴다.

## C. 원본 격리형 (isolate)

민감 정보가 코드의 입력 데이터다. 코드는 공개해야 하고 데이터는 공개할 수 없다. 실기기 계측 로그, 실주소가 든 테스트 픽스처, 개인 계정 덤프가 여기 해당한다.

**전제**: 저장소 안에서 지우는 것으로는 부족하다. 데이터는 저장소 **밖**으로 나가고, 저장소는 재유입을 구조적으로 막는다.

### 절차

1. **원본을 저장소 밖 private 폴더로 옮긴다.** 홈 디렉터리 아래 `~/<project>-private/` 같은 자리. 여기에 원본과 대응표를 둔다.
2. **`.gitignore`로 재유입을 막는다.** 파일명 패턴 단위로(`*-diag*.log*`). 도구가 자동 생성하는 종류라면 다음에 또 생긴다는 뜻이므로 패턴이 정확해야 한다.
3. **필요한 축만 익명화 fixture로 뗀다.** 테스트가 좌표를 필요로 하면 좌표를 지우지 말고 **변환**한다. 예를 들어 경도 평행이동은 거리와 방위를 보존하므로 알고리즘 테스트는 그대로 통과하면서 실제 위치는 사라진다. 좌표가 불필요한 테스트라면 시각과 이벤트만 남긴다. 지우는 것과 변환하는 것의 차이가 테스트를 살리고 죽인다.
4. **대응표는 private 폴더에 둔다.** 문서·테스트·커밋 메시지 어디서도 실제 값을 쓰지 않고 `자택`·`주택 A`·`대상자 1` 같은 라벨로 쓴다. 서술형 본문(코스 설명, 사례 설명)이 이 규칙을 가장 자주 어긴다. 표 형태의 데이터는 눈에 띄지만 문장 속 주소는 그렇지 않다.
5. **히스토리를 확인한다.** 데이터가 과거에 커밋된 적 있으면 SKILL.md 3단계로 간다. 이 유형은 파일이 크고 눈에 잘 띄어서 히스토리에 남아 있을 확률이 높다.

### 데이터 출처 표 (NOTICE.md)

격리하고 남은 데이터, 즉 **공개해도 되는** 정적 데이터에도 조건이 붙는다. 코드가 MIT라도 데이터는 원출처 조건이고, 명시하지 않으면 MIT로 오인된다.

| 파일 | 원출처 | 이용 조건 | 재생성 |
|---|---|---|---|
| (파일 경로) | (기관·데이터셋명·URL) | (라이선스·출처표시 의무) | (스크립트 경로) |

라이선스가 다른 원본에서 파생된 파일들은 한 파일로 합치지 않는다. 합치면 조건이 섞여 어느 쪽도 지킬 수 없다.

### fork 식별자 표 (docs/FORKING.md)

이 유형은 앱·서비스인 경우가 많아 fork하는 사람이 바꿔야 할 자리가 많다. 새 식별자를 코드에 박을 때마다 표에 자리를 더한다.

| 항목 | 위치 | 비고 |
|---|---|---|
| 도메인 | (파일:줄) | |
| 번들 ID·패키지명 | | |
| 연락처·계정 | | |
| API 키 이름 | | 값이 아니라 변수명 |

## 혼합 저장소

한 저장소가 여러 유형에 걸리는 것은 정상이다. 코드는 A, 계측 로그는 C, 업무 문서는 B인 저장소가 실제로 있다. 유형을 하나로 몰지 말고 영역별로 나눠 적용하되, 어느 영역이 어느 유형인지 판정 근거를 저장소 문서에 한 줄 남긴다. 근거가 없으면 다음 사람은 그 배치가 판단인지 우연인지 알 수 없고, 그 순간 규율이 무너진다.
