# 히스토리 재작성 (소급 층)

유형 A·B·C가 **앞으로 들어올 것**을 막는 층이라면, 이 절차는 **이미 들어온 것**을 되돌리는 소급 층이다. 공개 시점에는 둘이 거의 항상 함께 간다. 격리 없이 재작성만 하면 다음 커밋에 같은 것이 다시 들어오고, 재작성 없이 격리만 하면 과거 커밋이 그대로 남는다.

먼저 [필요 판정](#필요-판정)을 통과해야 이 절차를 시작한다. 판정을 건너뛴 재작성은 되돌릴 수 없는 작업을 근거 없이 하는 것이다.

## 필요 판정

**정보의 성질로 갈리지 않는다.** 팀 ID처럼 어차피 공개되는 식별자는 1,000건이 있어도 재작성 대상이 아니고, 주소처럼 있으면 안 되는 것은 1건이라도 대상이다. 그래서 순서가 둘이다.

### 1. 먼저 항목을 두 갈래로 나눈다

| 갈래 | 무엇 | 어디로 |
|---|---|---|
| **삭제해야 함** | 실명·주소·좌표·연락처·크리덴셜·제3자 정보 | 아래 판정으로 |
| **fork가 바꾸면 됨** | 도메인·번들 ID·팀 ID·패키지명·앱 이름·연락 메일 | `docs/FORKING.md` 표. 지우지 않고 남긴 채 "여기를 바꿔라"로 안내한다 |

이 분류를 건너뛰고 전부 지우면 fork가 불가능한 저장소가 된다. 식별자가 있어야 할 자리에 아무것도 없으면 외부 사용자는 무엇을 자기 값으로 채워야 하는지 알 수 없다.

### 2. 삭제 갈래에만 결정론 판정을 돌린다

```bash
python {skill_dir}/scripts/history_check.py <repo> --local
# 또는 치환표를 이미 만들었다면
python {skill_dir}/scripts/history_check.py <repo> --replace-text ~/<project>-private/replace-text.txt
```

항목마다 셋을 센다. 셋이 서로 다른 층이라 하나로 갈음되지 않는다.

| 검사 | 명령 | 뜻 |
|---|---|---|
| 파일 내용 | `git log --all -S'<좌변>'` | 과거 커밋의 파일 안 |
| HEAD 트리 | `git grep -F '<좌변>' HEAD` | 지금 체크아웃되는 파일 안 |
| 커밋 메시지 | `git log --all --format=%B` | **`--replace-message` 필요 여부를 여기서 정한다** |
| 삭제 경로 | `git log --all -- '<경로>'` | "지금 없다"와 "이력에 없다"는 다르다 |

- **전부 0**: 재작성 불필요. 유형 A·B·C만으로 공개할 수 있다. 처음부터 공개 전제로 만든 저장소는 대개 여기다.
- **하나라도 0이 아님**: 재작성이 필요하다. 그리고 **"그냥 비공개로 둔다"도 정당한 선택지다.** 실제로 재작성이 필요하다고 판정된 저장소 중 둘은 공개를 포기했고 하나만 재작성했다. 재작성이 필요한데 하지 않기로 했다면 그 저장소는 공개하지 않는다. 이 갈림은 **파괴적이고 외부로 나가는 작업**이므로 사용자에게 묻는다.

`history_check.py`는 검증하지 못한 항목(정규식 방언이 갈리는 패턴, 너무 짧은 좌변, git이 오류로 끝난 항목)을 0건이 아니라 **모름**으로 보고하고 깨끗 판정을 내리지 않는다. 0건과 "확인하지 못함"을 뭉개는 것이 이 층에서 가장 위험한 실패다.

## 9단계 절차

### 1. 트리 정제 커밋

로그 삭제, 익명화 fixture 전환, `.gitignore` 재유입 차단, `NOTICE.md`·`docs/FORKING.md`·`LICENSE` 신설을 **재작성 전에** 한 커밋으로 끝낸다. 재작성은 이 상태를 소급 적용하는 것이므로, 트리가 아직 더러우면 재작성을 두 번 하게 된다.

### 2. 백업 번들

```bash
git bundle create ~/<project>-private/pre-filter-repo-backup-$(date +%Y%m%d).bundle --all
git bundle verify ~/<project>-private/pre-filter-repo-backup-$(date +%Y%m%d).bundle
```

**번들은 치환표를 만들기 전 상태이므로 실값을 그대로 담는다.** 반드시 저장소 밖 격리 폴더에 두고, 클라우드 동기화 폴더나 공유 드라이브에 두지 않는다. <!-- sanitize: allow 규칙 서술 자신 --> 이 번들이 재작성을 되돌릴 수 있는 유일한 수단이다(reflog는 재작성 시점에 만료된다).

### 3. 스캔, 그리고 사람

```bash
gitleaks git --redact .
python {skill_dir}/scripts/scan_traces.py .
```

**gitleaks 통과는 PII 통과가 아니다.** gitleaks는 비밀값 패턴만 본다. 문서 본문에 문장으로 적힌 주소·실명·좌표는 어느 스캐너도 잡지 못하고, 실제로 그것을 잡은 것은 **별도 컨텍스트의 리뷰어**였다. 스캐너 뒤에 사람(또는 세션 히스토리를 넘기지 않은 서브에이전트)이 "로그 파일 밖 문서에 주소·실명·좌표가 있는지"를 읽는 단계를 계약으로 둔다. 생성 맥락을 아는 주체는 자기가 쓴 문장을 정상으로 읽는다.

### 4. 치환표 두 벌

격리 폴더에 둘을 만든다. 역할이 다르다.

| 파일 | 독자 | 내용 |
|---|---|---|
| `replace-text.txt` | 기계 | `원문==>치환` 한 줄씩. 표기 변형마다 한 줄(같은 장소의 다른 표기 7개면 7줄) |
| `places.md` | 사람 | 왜·어디를 적은 대응표. 실행한 명령도 여기 적는다(6단계) |

**정규식 대신 리터럴로 적는다.** filter-repo는 치환표를 바이트로 읽어 컴파일하고 검증 명령도 바이트를 세므로, 한글이 든 정규식은 치환도 역검증도 조용히 빗나간다(실측: 대상이 있어도 0건). 그래서 "표기 변형마다 한 줄"이 편의가 아니라 정확성의 요구다. `glob:` 줄은 경로가 아니라 내용 글롭이라 역검증에서 검증 불가로 막힌다.

`.sanitize.local.md`의 `## 치환` 표가 이미 같은 내용이면 그대로 내보낸다. **표를 둘로 나누지 않는 것이 요점이다.** 한쪽에만 등록된 표기 변형이 곧 이력에 남는 잔존이 된다.

```bash
python {skill_dir}/scripts/scan_traces.py <repo> --emit-replace-text ~/<project>-private/replace-text.txt
```

커밋 메시지에 등장한 좌변을 빠뜨리지 않는다. 판정의 메시지 열이 0이 아니면 `--replace-message`가 필요하다.

### 5. 실행

```bash
pip install git-filter-repo
git filter-repo \
  --path-glob '<지울 경로 패턴>' --invert-paths \
  --replace-text ~/<project>-private/replace-text.txt \
  --replace-message ~/<project>-private/replace-text.txt
```

부수 효과를 미리 안다.

- **`origin` 원격이 제거된다**(사고 방지 설계다). 확인 후 직접 되붙인다.
- **태그도 재작성된다.** 릴리스 태그가 있으면 전부 새 SHA를 가리키게 된다.
- **reflog가 만료된다.** 되돌릴 수단은 2단계 번들뿐이다.
- 커밋 메시지가 참조하는 옛 SHA는 그대로 남는다(filter-repo가 `suboptimal-issues`에 보고한다).

### 6. 실행 명령을 대응표에 적는다

`places.md`에 방금 돌린 명령을 **인자 조합 그대로** 붙여 넣는다. 이것을 빠뜨리면 나중에 무엇을 어떻게 지웠는지 재구성만 가능하고 확인은 불가능해진다(실측: 한 번에 돌렸는지 두 번 돌렸는지조차 판정할 수 없었다). 대응표는 격리 폴더에 있으므로 명령에 실값이 들어 있어도 된다.

### 7. 역검증

```bash
python {skill_dir}/scripts/history_check.py <repo> \
  --replace-text ~/<project>-private/replace-text.txt --path '<지운 경로 패턴>'
```

**전부 0이어야 한다.** 이 단계를 빠뜨린 실측 사례에서, 재작성 2분 뒤 다시 유입된 치환어가 그대로 공개되어 지금도 남아 있다(8단계). 좌변마다 파일 내용·HEAD·커밋 메시지 셋이 0인지, 지운 경로의 커밋 수가 0인지 기계로 확인한다. 눈으로 훑는 것은 검증이 아니다.

### 8. 후속 문서에 치환 전 값을 쓰지 않는다

**실사고.** 재작성 2분 뒤의 후속 커밋이 CHANGELOG에 "옛 파일명 → 새 파일명"을 적으면서, 방금 이력에서 지운 이름(단지명 포함)을 공개 저장소에 다시 박았다. 재작성 자체는 성공했는데 그 성공을 기록하는 문장이 유출원이 됐다.

원인은 도구가 아니라 **메타 정보를 아티팩트에 쓴 것**이다. 무엇을 무엇으로 바꿨는지는 작성 과정을 지켜본 사람에게만 의미 있는 정보이고, 최종 독자에게 필요한 것은 결과뿐이다. 그래서:

- 대응표(무엇→무엇)는 격리 폴더의 `places.md`에만 둔다.
- 공개 CHANGELOG·커밋 메시지·PR 본문에는 **"파일명과 지명을 일반형으로 바꿨다"까지만** 적는다.
- 부재를 설명하는 문장("실주소라 제외했음")도 같은 이유로 쓰지 않는다. 그 문장 자체가 무엇이 있었는지 알려 준다.

### 9. 재발 방지 층

`.gitignore`는 **파일 단위만** 막는다. 문서 본문에 문장으로 들어오는 텍스트는 아무것도 막지 못한다. 실측 저장소에서 CI·pre-commit 훅·재유입 테스트가 전부 없었고, "실주소 금지" 규칙을 신설한 지 2분 뒤 같은 세션이 그 규칙을 어겼다. 규칙 문서는 가드가 아니다.

pre-commit 훅 전문은 [tools.md](tools.md)의 「pre-commit 훅」 절에 있다. 요점 둘만 여기 둔다.

- 좌변 목록(`terms.txt`)은 실값이라 격리 폴더에 두고, **목록이 없으면 통과가 아니라 차단**이다. 격리 폴더를 옮기거나 다른 머신에서 클론하면 가드가 조용히 사라지는데, 그것이 이 층이 막으려는 실패 형태다.
- 텍스트 가드와 스캐너를 함께 건다. 앞은 아는 좌변을, 뒤는 홈 경로·크리덴셜처럼 목록에 없는 것을 잡는다.

## 재작성 뒤 남는 것

`git filter-repo`도 BFG도 다음에는 닿지 않는다. 저장소를 public으로 뒤집으면 이것들도 함께 공개된다.

- fork, 이미 배포된 클론
- GitHub가 캐시한 옛 SHA(force push 뒤에도 URL로 접근된다. Support에 gc를 요청할 수 있고, 요청하지 않기로 했다면 그 결정을 기록에 남긴다)
- CI 로그와 아티팩트, 릴리스 자산
- issue·PR 본문, 위키

**이미 어딘가 뿌려졌거나 판단이 서지 않으면 재작성보다 새 저장소 재생성이 안전하다**(SKILL.md 3단계). 히스토리를 잃는 대신 "빠뜨린 것이 없다"는 확실성을 얻는다.

다른 머신의 클론은 `git pull`이 아니라 **재클론**한다. 재작성된 이력과 옛 이력은 병합되지 않고, 잘못 병합하면 지운 커밋이 되살아난다.
